# Lessons — fundXI

One-line entries: date · what changed · why previous approach failed.

- **2026-05-10** — Added "Data Sourcing — NON-NEGOTIABLE" section to `CLAUDE.md`. Previous behaviour: I synthesised Wikipedia-style bio prose and an invented skills pool in PlayerSheet, even though the user had asked for "everything via Sportmonks → DB → UI". The previous approach conflated the *no-direct-provider-call* aspect with the broader *no-synthetic-content* spirit; documenting both rules explicitly stops future drift.
- **2026-05-12** — Always re-bootstrap (and rebuild derived data: `wc_replay`, `enrich_player_mentions`) after any TRUNCATE / `simulation.cli.wipe` run for a smoke test — never leave the DB partial. Previous behaviour: I wiped time-varying tables (`player_tournament_stat`, `player_daily_snapshot`, `match_event/comment/lineup`, `player_price_tick`) for smoke tests and only re-populated a single fixture, so the screener showed ~11 players (it derives its list from `player_price_tick`). Also: static data (teams/players/fixtures) must always be visible in views regardless of live-data presence — fixed the design flaw it exposed in `/api/players/screener-view` (it `WHERE lt.current_price IS NOT NULL`-filtered players instead of LEFT JOIN + synthetic-base-value fallback).
- **2026-05-19** — Verified the actual dataset before choosing a constant: my first `seed_baseline_ticks` used a fixed `TOURNAMENT_OPEN_TS = 2026-06-01`, assuming WC2026 dates. The local data is WC2022 (fixtures 2022-11-20), so a fixed-future ts would have created a second baseline tick *after* all match ticks → it becomes the latest tick → price snaps back to base. Caught by inspecting `valuation.player_price_tick` (829 existing baselines at 2022-11-19). Fix: derive the anchor ts from data (earliest kickoff − 1 day), matching `wc_replay`'s formula so the two seeders dedupe on the PK. Lesson: a "constant" that encodes an assumption about live data is a verified-knowledge violation — derive it or check the DB first.
- **2026-05-20** — When adding a UI info element (icon, badge, value) on one surface, immediately mirror it to ALL other surfaces showing the same info for the same entity, in the same commit. I added goal/card badges only to the pitch tokens (PitchView) without applying them to the list cards (RosterCard), and the user had to point it out. Extracted a shared `MatchEventBadge` component to make the symmetry structural. Memory: `ui-coherence-symmetry`.
- **2026-05-30** — When testing Expo Go on a physical iOS device and it shows "the internet connection appears to be offline" while the phone's browser reaches the dev server and general internet works, check the **iOS Local Network permission for Expo Go FIRST** (Settings > Expo Go > Local Network). iOS blocks per-app LAN access; denied → Expo Go can't contact the dev server and mislabels it "offline" without ever making a request. I burned ~2h chasing firewall/tunnel/QR/subnet/VPN before the user found the toggle. Diagnostic signal: the dev-server log shows **zero** incoming native bundle requests — the request never leaves the phone.
- **2026-06-01** — A cross-package parity test belongs to the package that owns the obligation, not to `packages/core`. I added a "web theme.css mirrors the palette" test inside `core/src` using `node:fs` to read `apps/web/...`; this forced node builtins into core's pure (no-node/no-DOM) src and inverted the DDD dependency direction (core must know nothing about apps), and it broke `tsc`. Reverted. Lesson: before placing a check, ask which layer owns the invariant — a guard over web's hand-mirrored file is a web-side concern; core stays pure. Also: `RN custom fonts` — variable fonts have limited platform support on Expo, so bundle STATIC per-weight files under one family via the `expo-font` config plugin (keeps `fontWeight` working without refactoring every style); it embeds at dev/prebuild, not in Expo Go.
- **2026-05-30** — The installed Expo Go's supported SDK is a hard constraint: pick the project's Expo SDK to match the device's Expo Go BEFORE migrating. We had drifted to SDK 56/55; the released Expo Go on the phone was SDK 54, so nothing could ever load. Verify the device's Expo Go SDK first, then pin `expo` + RN + react + every native module to that SDK's `bundledNativeModules.json` (don't guess versions). Also: in an npm-workspaces monorepo, npm may nest some of `expo`'s own deps under `node_modules/expo/node_modules`, so Metro's `resolver.disableHierarchicalLookup` must stay `false` or those nested deps (e.g. `expo-asset`) are unresolvable.
